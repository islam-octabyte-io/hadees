# Reader frontend: generated API types, one page-block component, and print structure instead of cards

The `frontend` workspace now reads the corpus. It consumes the API from ADR 0002 unchanged — no endpoint was added, and search is still absent — so the whole of the work is in three places: how types and requests reach the client, which components exist, and what the reader looks like.

## Considered options

**API access: `openapi-fetch` + `openapi-typescript`, mirroring the Quran frontend.** `pnpm gen:api` generates `src/lib/api/schema.d.ts` from the live backend's `/docs-json` and the result is committed, exactly as the sibling project does it. The backend's DTOs are `nestjs-zod` schemas with `.describe()` on their fields, so the generated document already carries accurate request and response types — hand-written types would only drift. The alternative, a checked-in spec file, was rejected for the same reason: it adds a second thing to keep in sync.

Everything else lives in one module, `src/lib/api/client.ts`: a private `ApiError`, an `unwrap()` that turns a non-2xx into a throw, one thin wrapper per route, and an `orNull()` that swallows 400 and 404 so routes can call `notFound()` while a broken backend still surfaces as an error page. Two departures from the sibling, both deliberate: the corpus is immutable once seeded, so `next: { revalidate }` is set **once** on `createClient` (openapi-fetch spreads its base options into every request) rather than repeated on sixteen wrappers; and `getBooks`/`getEditions`/`getBookIndex` are wrapped in React `cache()`. The sibling re-fetches its index on all ninety of its division pages, which is the specific waste being avoided.

`HadithDto` carries only a `bookPrefix`, so anything rendering a narration outside its own book page needs the collection list to name it. `getBookIndex()` returns books keyed by slug, prefix and UCI for exactly that.

**Bilingual by default, against the API's own default.** `?edition=` defaults to `ar-vocalized` server-side; the reader asks for `ar-vocalized,ur-darussalam` everywhere. The only translation in the corpus is Urdu and the audience reads it, so Arabic-only would be a setting almost every reader changes on arrival. `resolveEditions()` filters a `?edition=` CSV against what the corpus actually has, which also means the frontend can never send an unknown slug and provoke a 400.

A narration's `texts` array can be short or empty — roughly forty narrations are missing a row in one edition and one has neither — so panes are rendered by iterating the *requested* editions and looking each one up by slug. Nothing indexes `texts[0]`.

**Citation lookup instead of search.** There is no `/search` endpoint, and the copy never implies one. Instead the corpus is addressed the way it is cited: one mono input accepts everything the API accepts, and a Server Action resolves it and redirects. It is a `<form action={…}>` rather than client-side fetching, so it works with JavaScript disabled.

One ambiguity had to be settled. `bukhari:3` is a valid hadith address *and* a valid kitab address. Citation form wins — a collection and a number means that narration, because that is what a footnote means by it. Kitabs and baabs stay reachable by UCI (`HK3`) and by the three-part form (`bukhari:3:5`), and the hint under the input teaches exactly that rather than describing a grammar the resolver does not implement.

**The UCI is declared canonical, not redirected to.** Several identifiers resolve to the same narration. Rather than redirect the aliases, `/hadiths/[identifier]` renders them and sets `alternates.canonical` to the UCI form. The page is identical either way, so a redirect would only cost a round trip — and, as below, a mid-stream redirect in Next 16 degrades to a client-side one anyway.

**Design: the annotated critical edition, not illuminated scripture.** The Quran frontend is parchment, gold leaf and lapis with an inscriptional Latin display face. Hadees shares its Arabic and Urdu type with that project — Amiri for vocalized naskh, Noto Nastaliq Urdu for the translation — so the two read as one family, and diverges everywhere else, because the artifact is different: a hadith collection is printed, graded, cross-referenced and annotated.

- **Ink on paper, on a board.** Six named `oklch` values in `globals.css`: `--board` (the desk), `--paper` (the reading surface), three weights of iron-gall `--ink` for matn, translation and apparatus, and a madder `--rubric`. The shadcn tokens are remapped onto these, so every primitive inherits. `--primary` stays ink: the rubric marks structure — baab titles, numerals, gradings, focus rings — and never fills a button.
- **No cards.** A narration is a page block inside a *jadwal*, the ruled double frame of a printed page, drawn as a border plus an offset outline so it stays one element. The hadith number sits in a rubric medallion straddling the frame's edge in the margin; the hashia sits under a short foot-rule; the citation and grading are apparatus beneath. Each of those maps to a real API field.
- **Latin is never display type.** The corpus contains no English, so Latin here is labels, counts, UCIs and citations — set in IBM Plex Mono as tracked catalogue caps, with IBM Plex Sans for the little prose there is. The only display faces are the corpus's own scripts. Geist was removed entirely.

**RTL is per element, not a document flip.** `<html>` stays `lang="en"` with no `dir`, and `components.json` keeps `rtl: false`. The chrome is LTR English; direction is opted into by `ScriptText`, which takes the API's own `language` code and applies `dir`, `lang`, the right face and its leading. A global flip would mirror the pagination and navigation too. `letter-spacing` is reset in `.script-arabic`/`.script-urdu` because tracking breaks Arabic cursive joins.

**Corpus text carries a little markup, and only two tags are real.** About a third of `hadith_texts` rows contain `<br>` where a paragraph breaks and `<span class="heading-color">` around a commentary heading such as `تشریح :`. Left alone these render as literal angle brackets mid-translation. A generic tag-strip is not available: angle brackets are *also* used as quotation marks around Arabic speech (`<، قَالَ: أَصَبْتُ أَهْلِي>`), so `parseCorpusText` handles `br` and `span` and nothing else. Markup becomes structure — the heading is promoted to the rubric — and nothing is ever rendered as HTML.

## Consequences

- **Components exist because they are used more than once.** `KitabDto` and `BaabDto` are structurally identical, so one `Fihrist` renders both levels from a small adapted shape. One `HadithEntry` serves the baab reader, the continuous stream and the permalink, which is why that component is where the corpus's holes are handled. `ScriptText` is the single funnel for every Arabic and Urdu string, and `CorpusText` for every one that comes from the corpus. Only three shadcn primitives are installed (`button`, `input`, `skeleton`); `card`, `badge`, `breadcrumb`, `pagination` and `sheet` are replaced by purpose-built pieces that fit the print language.
- **Route params arrive percent-encoded.** Next 16 hands `/hadiths/bukhari:100` to the page as `bukhari%3A100`, and openapi-fetch encodes path params again on the way out, so the double encoding stops the API resolving the citation. `decodeIdentifier()` exists for that and is applied wherever a param carries the identifier grammar. This cost real debugging time; it is not obvious from the type.
- **`notFound()` can only set a 404 status where the params are enumerable.** Once a response streams, Next cannot change the status code; it injects `<meta name="robots" content="noindex">` instead. Books (15) and kitabs (503) are therefore prerendered with `generateStaticParams` and `dynamicParams = false`, so an unknown slug is rejected before rendering and answers a real 404. Baabs (14,749) and narrations (41,998) are too numerous for that and answer 200 with `noindex`. The upside is that 523 pages are static, and the build still takes about eight seconds.
- **The edition picker lives on the reader pages, not in the header.** Reading `useSearchParams` in a layout-level component suspends, which starts the stream and takes the 404 status away from every page beneath it. Passing the resolved editions and the surrounding query down as props removes the hook entirely. It is also the better placement: the control only means anything where there is text to show.
- **A stale `next-server` will silently serve old code.** `pnpm start` fails with `EADDRINUSE` and leaves the previous build answering on the port. Two conclusions during this work were drawn from a stale server and had to be redone; kill by PID and confirm the new process bound before trusting any measurement.
- Book URLs are slug-only (`/books/bukhari`). The API also accepts `HZ1` and `1`, and the lookup bar still resolves those, but they are not routes — `dynamicParams = false` is what buys the real 404.
- Adding an edition stays a data-only change on the frontend too: the picker, the panes and the metadata all derive from `GET /editions`.
